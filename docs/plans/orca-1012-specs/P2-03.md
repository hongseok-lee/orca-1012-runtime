# P2-03 — Snapshot manifest·호환성·명시 선택·CONSUMED

상태: 구현 미착수 · 단계: Phase 2 / 착수 묶음 6.
선행: [P1-02](P1-02.md)·[P1-10](P1-10.md)·[P1-11](P1-11.md), [P2-01](P2-01.md)·[P2-02](P2-02.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §10.2·§10.5–6·§10.8.5. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

Snapshot을 정확한 실행·파일·provider 이력에 연결하고 재사용 가능 여부를 판정한다. 수정 경계는 manifest schema/repository, compatibility 검사, 명시 restore 선택과 consumption transaction이다.

## manifest 계약

- Snapshot/provider resource/checkpoint ID, Runtime Unit·source attempt/epoch, image digest·provider/adapter/schema/runtime compatibility를 기록한다.
- storage binding/epoch/seal/mount identity, Session/provider lineage/checkpoint·admitted/settled input watermark·durable event cursor·context/cancel revision을 기록한다.
- Tab membership/revocation revision, capture mode, restore gate contract version을 보존한다.
- PREPARING→READY_SEALED, CONSUMED/INVALID/FAILED를 실제 증거에 따라 관리한다. FROZEN_TURN은 P2-10 검증 전 활성화하지 않는다.

## 판정·소비 계약

1. 같은 Agent/Runtime Unit의 명시 Snapshot만 선택한다. 임의 최신/다른 Agent의 동일 spec Snapshot을 허용하지 않는다.
2. 이미지/CLI/runtime/spec·자원·provider watermark·storage seal과 현재 상태를 대조한다. 새 Pod UID/attempt에 결합된 새 ticket을 사용한다.
3. DB에만 쌓인 새 입력, 이름/핀/읽음 변경 등 전체 DB revision 변화만으로 폐기하지 않는다. provider 전달/파일 writer 재허용/native mutation/계정·권한 변경은 관련 조건을 다시 판정한다.
4. 최신 취소/context/질문/closed Tab을 대조한다. 최초 구현은 전체 member 구성이 달라지면 cold로 전환한다.
5. **현재 실행의 첫 쓰기 전에** 원 Snapshot을 CONSUMED로 하고 storage epoch를 증가시킨다. OOM 자동 복원이 이미 소비한 과거 메모리를 재사용하지 못해야 한다.

## 완료·검증 기준

다른 Agent/동일 spec·이미 CONSUMED·stale 파일·CLI 변경·member 변경·새 DB 입력·이름 변경을 각각 검증한다. 첫 쓰기와 consumption 경합에서 재사용 가능한 Snapshot이 남지 않으며 취소/닫힌 Tab이 부활하지 않는다. 판별 불명은 gate를 닫고 cold로 전환한다.

## 산출물·연계

manifest/compatibility/consumption 구현과 identity·첫 쓰기 경계 증거를 제출한다. P2-04의 capture와 P2-05의 resume가 같은 계약을 사용한다.
