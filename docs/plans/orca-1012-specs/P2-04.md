# P2-04 — 정상 quiescent checkpoint-and-stop

상태: 구현 미착수 · 단계: Phase 2 / 착수 묶음 6.
선행: [P1-13](P1-13.md), [P2-01](P2-01.md)~[P2-03](P2-03.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §9.3·§10.3. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

정상 휴면 시 전체 Runtime Unit을 일관된 상태로 checkpoint하고 실제 실행을 정지한다. 수정 경계는 QUIESCING barrier, flush/watermark, process park·seal·checkpoint-and-stop operation이다.

## capture 순서와 계약

1. 새 입력은 DB에 계속 접수하되 provider 전달을 닫는다. 이미 진행 중인 dispatch도 barrier에 포함한다.
2. 모든 member의 active turn/tool/background writer가 정지 가능한지 확인한다. 현재 효과가 진행 중일 수 있는 attempt나 미확인 writer가 남으면 quiescent 완료로 기록하지 않는다.
3. provider session/파일 flush와 마지막 producer event의 중앙 commit watermark를 맞춘다. 과거 UNKNOWN 이력만 있고 현재 실행/쓰기 부재가 확인된 경우 이력 자체를 휴면 금지 사유로 삼지 않는다.
4. 복원 후에도 닫혀 있을 process tree gate로 park한 뒤 storage seal/provider/input watermark를 확정한다.
5. checkpoint-and-stop을 수행하고 Snapshot Ready와 실제 execution stopped를 별도로 관측한 뒤 READY_SEALED/SUSPENDED로 기록한다.
6. checkpoint 후 계속 쓰는 resume 모드를 기본 휴면으로 쓰지 않는다. bare Pod/Deployment·restartPolicy의 실제 재시작 동작을 실험해 root가 적용 경로를 확정한다.
7. 실패 시 active 작업 부재를 다시 확인하고 세션 저장 후 안전한 cold stop으로 전환한다. Snapshot 성공 전에 프로세스를 먼저 종료해 메모리를 잃지 않는다.

## 완료·검증 기준

새 입력/sleep/close, 여러 member 중 한 작업 active, background writer, dispatch EFFECT_POSSIBLE, flush/event commit 지연, Snapshot API 성공 후 실행 지속, 자동 재시작을 검증한다. Snapshot Ready만으로 stopped를 선언하지 않으며 한 Tab sleep/close로 다른 작업이 종료되지 않는다.

## 산출물·연계

quiescent/flush/park/seal/stopped 증거와 operation crash 인수 결과를 제출한다. active turn 이동은 P2-10의 FROZEN_TURN으로 별도 검증하며 이 작업의 QUIESCENT로 표시하지 않는다.
