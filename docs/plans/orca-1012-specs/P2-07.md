# P2-07 — 원래 request로 복원 후 gate 안에서 증량

상태: 구현 미착수 · 단계: Phase 2 / 착수 묶음 6.
선행: [P2-01](P2-01.md)·[P2-05](P2-05.md)·[P2-06](P2-06.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §10.8.9·§18. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

Snapshot 복원 중 더 큰 자원이 필요할 때 원래 request로 메모리를 복원한 뒤 닫힌 gate 안에서 resize한다. 수정 경계는 restore/resize operation 합류, gate release 조건, 실제 identity/연속성·자원 판정이다.

## 구현 계약

1. 호환되는 Snapshot의 원래 request로 복원한다. 직접 target RAM request 복원이 가능하다고 가정하지 않는다.
2. provider·자식·background task의 gate를 닫아 작은 request에서 먼저 작업·파일/외부 효과가 시작되지 않게 한다. 인증된 control-plane resize/조회는 수행할 수 있어야 한다.
3. P2-06의 같은 operation/예산 계약으로 target request를 적용하고 실제 applied resources를 확인한다.
4. 실제 Snapshot identity·복원 process/memory 연속성·단일 실행/RW 권한·최신 취소/context·첫 쓰기 전 consumption 조건을 함께 확인한 뒤 gate를 연다.
5. Deferred/Infeasible/기한 초과는 실제 상태 재조회와 유한 기한으로 판단한다. 응답 유실만으로 중복 증량·즉시 강제 종료하지 않는다.
6. 복원/resize 적용이 불가능하면 실패 실행의 안전한 종료/RW 회수 뒤 target profile로 explicit cold 복구한다. 입력·UNKNOWN과 기존 Session/Tab을 보존한다.
7. 같은 Node 이름을 실패 사유로 삼거나 별도 headroom gate를 추가하지 않는다. 실제 Agent·NFS·압박·다른 노드 경계를 검증한다.

## 완료·검증 기준

원래 크기 복원→닫힌 gate resize→실제 적용→실행 허용 순서를 증명한다. gate 이전 provider/자식의 파일·네트워크 효과는 0이어야 한다. 성공·응답 유실·Deferred/Infeasible·실패 cold와 다른 노드/메모리 압박을 실제 provider별로 검증한다.

## 산출물·한계

복원/resize 합류 코드와 identity·continuity·gate·NFS·fallback 증거를 제출한다. 합성 live 성공은 이 경로의 통합 합격을 대체하지 않으며 이 작업의 실패 시험도 P2-06 자체 live 실패 시험을 대체하지 않는다.
