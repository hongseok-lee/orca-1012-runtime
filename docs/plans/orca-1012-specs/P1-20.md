# P1-20 — 출력 journal·native history·UI projection 정합성

상태: 구현 미착수 · 단계: Phase 1 / 착수 묶음 3.
선행: [P1-03](P1-03.md)·[P1-11](P1-11.md), [P1-16](P1-16.md)~[P1-19](P1-19.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §6–7·§13. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

provider 출력·native history·Catalog/Chat 상태를 같은 영속 사실에 연결한다. 수정 경계는 output journal, nativeChat.readSession/subscribe, 공통 projection, clientEvents와 reconnect/reset이다.

## 구현 계약

1. provider event→canonical ID→PG commit→publish 순서를 지킨다. native identity/lineage와 producer incarnation/sequence로 중복을 막는다.
2. journal epoch/cursor는 단순 Pod 교체로 바꾸지 않는다. reconnect에 replay를 제공하고 보존 범위 밖이면 기존 reset/snapshot 계약으로 수렴한다.
3. native transcript와 영속 journal의 기존 frame·message ID·pagination을 유지한다. Pod 0에서 읽을 수 있으며 NFS/DB 오류를 빈 대화로 반환하지 않는다.
4. Catalog list/subscribe, worktree.ps/변경 이벤트는 같은 projection/revision을 쓴다. runtime.clientEvents는 commit된 변경을 invalidate하고 유실 시 full fetch로 복구한다.
5. 중앙 접수 bubble과 provider echo는 같은 Message라는 증거가 있을 때만 합친다. 본문 hash 일치만으로 다른 입력을 삭제하지 않는다.
6. pending·실제 모델 작업·준비·관측불명을 기존 working/active/permission 의미 안에서 표현한다. 준비 상태를 실제 작업으로 계측하거나 permission을 모든 인프라 실패 표시에 쓰지 않는다.
7. close/tombstone이 늦은 출력·binding·Snapshot 재등록보다 우선한다. 새 미지원 frame이나 가짜 provider ID로 UI를 강제로 열지 않는다.

## 완료·검증 기준

V1-01/08/13에서 Pod 0 history, 최초 빈 대화와 기존 cold open, commit/publish crash, 느린 subscriber, replay/reset, Active 교체, 늦은 Tab 재등록을 검증한다. 서로 다른 ID의 같은 본문이 보존되고 조회·구독이 같은 상태를 보인다. 미저장 출력을 영속 결과로 표시하지 않는다.

## 산출물·연계

projection/handler 대응표·journal identity와 실제 reconnect/history 증거를 제출한다. P1-14의 최종 공개 HA 통합에 합류하며 출력 단계 지연은 P1-28에 연결한다.

## 병렬 납품 경계

P1-03 journal, P1-11 event identity, P1-16 projection 계약을 확정하면 journal/replay/projection 기반을 먼저 작성한다. P1-03 영속 primitive나 P1-16 projection을 별도로 복제하지 않는다. provider/native history와 P1-17~19 공개 adapter는 준비된 부분부터 연결하고, ID 전체 완료는 모든 실제 출력·history·reconnect 조합이 합류한 뒤다.
