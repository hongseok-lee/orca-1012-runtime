# P1-15 — 6시간 관측 장애 episode·fresh 회복

상태: 구현 미착수 · 단계: Phase 1 / 착수 묶음 3.
선행: [P1-12](P1-12.md)·[P1-13](P1-13.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §9.4·§15. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

실제 상태를 장기간 확인할 수 없는 실행을 영속 episode로 관리한다. 수정 경계는 observation episode/watermark/deadline, fresh 상태 판정과 fencing operation 전환이다. 6시간을 정상 작업의 최대 실행 시간으로 사용하지 않는다.

## 구현 계약

1. Runtime Unit·attempt·Pod UID·execution epoch·시작 watermark와 최초 관측 상실 시각을 저장한다. deadline은 최초 시각+6시간이며 DB 시간으로 판단한다.
2. 과거 spool/event, 단순 HTTP 200, controller 교체, 옛 timer로 deadline을 연장하지 않는다.
3. 현재 attempt/epoch의 fresh IDLE 또는 WAITING_INPUT도 관측 회복이다. 실제 업무 활동 시각을 함께 늘리지는 않는다.
4. 6시간 DB deadline에서 실제 fencing operation을 시작한다. 차단 증거가 나오기 전 새 RW를 금지하며 실패/불명은 BLOCKED·알림으로 남긴다.
5. 새 6시간 차단 완료 SLA를 만들지 않는다. 정상 관측되는 장기 작업을 시간이 지났다는 이유로 종료하지 않는다.

## 완료·검증 기준

- V1-10: 5h59m에 fresh IDLE/WAITING_INPUT을 받아 episode가 회복되고 과거 타이머가 실행을 종료하지 않는다.
- 오래된 spool·다른 attempt/epoch 결과·HTTP 응답만으로 회복 처리되지 않는다.
- Active 교체 뒤에도 원 deadline이 유지되며 만료 시 fencing을 시작한다.
- 차단 실패/불명에서는 새 writer가 없고 BLOCKED 원인·알림이 남는다. 정상 6시간 초과 작업은 계속된다.

## 산출물·연계

episode/deadline 전이·fresh 판정과 시간 경계 증거를 제출한다. RV-04와 V1-10에 따라 시작 기한과 실제 차단 완료 증거를 별도로 기록한다.
