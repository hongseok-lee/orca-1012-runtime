# P2-05 — snapshot-first resume·재시도·명시 cold fallback

상태: 구현 미착수 · 단계: Phase 2 / 착수 묶음 6.
선행: [P2-03](P2-03.md)·[P2-04](P2-04.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §10.5–7. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

유효 Snapshot을 먼저 시도하고 복원 불가 시 기존 cold native 경로로 안전하게 수렴한다. 수정 경계는 wake/restore operation, manifest 선택·ticket binding·gate release, retry/deadline과 explicit cold 생성이다.

## resume 계약

1. DB에서 새 attempt/epoch를 예약하고 입력을 계속 접수한다. 이전 실행 차단과 READY_SEALED identity/storage/provider/runtime 조건을 확인한다.
2. 정확한 Snapshot을 명시 선택하고 새 Pod UID/attempt에 결합된 ticket으로 인증한다. 실제 복원 identity를 manifest와 대조하며 event 누락을 cold 증거로 단정하지 않는다.
3. 최신 질문/context/cancel/closed Tab/member를 중앙 DB 기준으로 확인한다. P2-03의 CONSUMED+storage epoch commit을 첫 쓰기 전에 수행한다.
4. 외부 provider/MCP/SSH 연결과 실제 provider readiness를 복구한다. Pod Running만으로 완료하지 않는다.
5. 같은 Tab/handle에 bind하고 watermark 이후 아직 미전달인 Message만 순서대로 보낸다. 새 Session/Tab을 만드는 fallback을 하지 않는다.

## retry·실패 계약

- 동일 유효 manifest의 일시 오류는 **총 최대 3회**, 2초/5초 backoff로 시도한다. 성공 시 즉시 끝낸다.
- stale/CONSUMED/다른 Agent/확정 불호환은 3회를 소모하지 않고 즉시 cold로 전환한다.
- 매 retry 전 실패 실행의 정지·seal 불변을 확인한다. scheduling 대기와 restore 자체 예산을 분리해 DB deadline으로 보존한다.
- 실패한 restore를 fence/종료한 뒤 Snapshot policy에 매칭되지 않는 검증된 spec/selector/disable 경로로 cold Pod를 만든다. 내부 변수만 cold로 바꾸고 플랫폼 자동 복원을 남기지 않는다.
- 같은 영속 파일·native session·receipt/turn/context를 대조해 재개한다. 특정 Agent policy를 비활성화할 때 다른 Agent의 policy를 삭제하지 않는다.

## 완료·검증 기준

유효 복원 성공·일시 오류 1/2/3회·확정 무효·응답 유실·Active 교체·scheduling 지연·플랫폼의 실제 cold fallback을 검증한다. retry 중 stale seal/첫 쓰기 이후 재사용이 차단되고 입력/UNKNOWN·취소 이력이 유지된다. 과거 4~7초 실험을 현재 latency 보장으로 쓰지 않는다.

## 산출물

resume/retry/fallback 코드와 실제 Snapshot identity·fence·ticket·provider readiness·Message 전달 증거를 제출한다.
