# G-03 — 실제 자원 admission·최소 profile·노드 배치 검증

상태: 증거 미확보 · 구분: 자원 기능 활성화 gate.
환경 선행: [P1-01](P1-01.md). 연계: [P1-21](P1-21.md)~[P1-24](P1-24.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §10.8.2–3·§16·§18. [공통 계약](COMMON.md)을 적용한다.

## 목적과 범위

새 환경에서 실제 Agent 이미지와 sidecar/initContainer 전체가 허용받는 CPU/RAM·limit·배치 조건을 확인한다. 과거 최소 `50m/52Mi`는 참고이며 현재의 provider 실행 성공을 증명하지 않는다.

## 확보할 계약·자료

1. requested, admission 이후 admitted, 실행 중 applied 자원을 구분해 기록한다. dry-run뿐 아니라 생성된 실제 Pod와 provider 시작 결과를 확인한다.
2. memory limit 필드 생략·CPU limit 미설정이 정책/defaulting 이후에도 유지되는지 확인한다. LimitRange/ResourceQuota와 admission mutation의 영향을 기록한다.
3. 1 Runtime Unit/Node 조건, Agent/다른 사용자 workload 동거, sidecar/initContainer 요구량과 노드 압박 증거를 수집한다.
4. 실제 최소 profile과 CPU:RAM 제약, quota·예약·old/new 중첩 자원 비용을 확인한다. core가 사용할 수 있는 사실과 미확인 조건을 분리한다.
5. 16Gi·2배·60분 등 초기 정책값을 실측 최적값으로 선언하지 않는다. 실제 workload 결과와 policy revision을 연결한다.

## 완료·검증 기준

- 선언한 최소 profile에서 실제 Claude/Codex의 시작·readiness 범위를 확인한다. admission 성공만으로 모델 실행 성공을 판정하지 않는다.
- limit 주입·quota 부족·배치 불가·CPU:RAM 제약을 각각 식별하고 RESOURCE_WAIT 등 실제 사유로 남긴다.
- 동시 예약과 old/new 중첩에서도 정책/예산을 초과하지 않는다. 자원 부족을 새 OOM 증거로 간주하지 않는다.
- 실제 isolated-node 조건이 확인되지 않으면 exit137 등만으로 자기 메모리 부족이라고 분류하지 않는다.

## 산출물과 범위 밖

환경/revision별 자원 대응표, Pod/Node·정책 증거와 provider 기동 결과를 제출한다. 새로운 Orca node-headroom gate는 추가하지 않는다. RV-06/08은 실제 증거를 확보하기 전에는 해결 완료가 아니다.
