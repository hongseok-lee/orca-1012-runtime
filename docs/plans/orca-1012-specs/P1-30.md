## 완료 판정

1. 각 행을 실제 소스/image/config/schema/policy revision 및 재현 가능한 결과 경로와 연결한다. 합성/실제 provider·정적/실기기 결과를 구분한다.
2. 필수 invariant `accepted-without-row`, `duplicate active writer`, `stale grant accepted`, `closed Tab resurrected`는 모두 0이다. UNKNOWN·queue/reconcile/replay·자원 예산의 관측도 제출한다.
3. G-02의 확인된 미지원과 아직 확인하지 않은 미검증을 구분한다. 미검증 행을 성공으로 바꾸거나 지원을 광고하지 않는다.
4. 기존 합격 증거는 동일 코드/환경이며 새 실패·우려가 없을 때 재사용한다. 변경된 경계와 누락된 실제 조합을 검증한다.
5. root는 통과 범위·실패·남은 제한을 검토해 Phase 1 완료 여부를 판정한다. 코드 작성·리뷰 통과만으로 완료하지 않는다.

## 범위 밖·산출물

추가 자동 계속 U-01, 조건부 과거 DB 복원 C-01, Phase 2 Snapshot/live/mid-turn을 새 Phase 1 gate로 넣지 않는다. 검증 행렬·invariant/성능 결과·재현 증거·제한을 통합한 완료 보고를 제출한다.

## 병렬 검증과 PR 증거

확정된 V1 수용 조건의 시험 코드와 fixture는 앞선 구현과 함께 준비하며, 실제 구현된 경계부터 원격 개발환경에서 검증한다. 독립 DB/Session·provider·기기 조합은 병렬 배분하고 공유 장애 주입·migration·동일 실기기 점유는 직렬화한다. 구현을 그대로 복사한 시험으로 계약 검증을 대신하지 않는다.

각 PR의 명세·변경·최신 revision·스크린샷·검증 결과를 수용 조건에 연결한다. root의 PR 리뷰/머지와 P1-30 전체 완료는 별도 판정이다. Expo Web 화면 결과를 native iPhone 설치 앱이나 실제 writer/HA 장애 증거로 확대하지 않는다. 전체 합격은 원래 P1-01~29·G-01~05 조건 충족 후다.
