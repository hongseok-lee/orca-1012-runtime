# P2-01 — 실제 substrate·복원 전 process tree gate PoC

상태: 구현·실증 미착수 · 단계: Phase 2 / 착수 묶음 6.
선행: [P1-09](P1-09.md)~[P1-11](P1-11.md), [P1-30](P1-30.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §10.1·§10.4·§16. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

새 GKE/runtime/CRD에서 memory restore를 안전하게 활성화할 수 있는지 실증한다. 수정/실험 경계는 명시 Snapshot 선택·restore identity, supervisor/substrate 실행 차단과 새 ticket binding이다. substrate별 사실 자료를 제출하고 최종 구현 경로는 root가 판정한다.

## 필수 gate 계약

1. 복원된 provider·전체 자식 프로세스·분리 background task가 filesystem/network 효과를 내기 전에 정지해 있어야 한다.
2. checkpoint 전 park된 상태가 restore 후에도 유지되어야 한다. supervisor가 복원되더라도 과거 env token·메모리 lease·옛 허가를 재사용하지 않는다.
3. 현재 Pod UID·attempt·execution epoch와 제어기/플랫폼 identity로 검증된 새 ticket이 있어야 실행을 풀 수 있다. 자체 생성 nonce만으로 인증하지 않는다.
4. initContainer/entrypoint의 검사만으로 대체하지 않는다. 메모리 복원은 entrypoint를 재실행하지 않을 수 있다.
5. 정확한 Snapshot 이름·외부 manifest·검증된 runtime 증거를 대조한다. event 누락을 cold start 증거로 간주하지 않는다.
6. gate가 닫혀 있어도 인증된 control-plane의 상태 조회·resize·context 준비는 가능해야 한다. 앱의 durable intake 자체를 막는 gate가 아니다.

## 완료·검증 기준

- 실제 provider/자식/background task의 파일·네트워크 시도로 새 ticket 이전 효과가 차단됨을 확인한다.
- supervisor 상태까지 복원한 경우, 제어면 단절, stale ticket/다른 Pod identity에서 gate가 열리지 않는다.
- 다른 Agent/동일 spec Snapshot이 선택되지 않으며 실제 복원 identity를 확인한다.
- 실패/판별 불명은 gate 닫힘과 명시 cold 재생성으로 처리한다. PoC 실패 substrate의 memory restore는 활성화하지 않는다.

## 산출물·한계

실제 플랫폼/runtime/CRD/image revision, process tree/gate/identity 증거와 통과 범위를 제출한다. 과거 CPU 직접 복원 성공·RAM 직접 복원 실패·합성 same-node 성공을 현재 실제 Agent 합격으로 대체하지 않는다. 이 Phase 2 gate는 Phase 1 cold 기능의 완료를 막지 않는다.
