# P1-23 — OOM·메모리 eviction 후 cold 증설 복구

상태: 구현 미착수 · 단계: Phase 1 / 착수 묶음 3.
선행: [P1-11](P1-11.md)·[P1-13](P1-13.md)·[P1-21](P1-21.md)·[P1-22](P1-22.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §10.8.4–7. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

확인된 메모리 부족을 하나의 영속 recovery operation으로 복구한다. 수정 경계는 incident→profile/예약→fence→새 attempt→provider binding을 잇는 controller 단계다. Phase 1의 복구는 명시적 cold native resume다.

## 구현 계약

1. dedup된 incident와 현재 intent/policy revision으로 목표 profile·reservation·operation을 원자적으로 정한다. 같은 incident를 재관측해 이중 증설하지 않는다.
2. 기존 writer의 실제 차단과 옛 자원 정리 후 새 attempt를 생성한다. K8s 응답 유실은 결정적 identity와 실제 결과 조회로 인수한다.
3. 새 Pod의 실제 admitted CPU/RAM·limit 생략·배치와 승인 예산을 확인한 뒤 동일 Session/Tab/native handle에 연결한다.
4. stale/OOM 이전 Snapshot을 복구에 자동 선택하지 않는다. 원 Message·Component·receipt·UNKNOWN/context를 보존하고 입력을 다시 접수하지 않는다.
5. 새 cancel/close·최신 intent가 복구보다 우선한다. 취소된 작업이나 닫힌 Tab을 새 attempt에서 되살리지 않는다.
6. Ready나 새 Pod 이름만으로 episode·24h 예산을 초기화하지 않는다. 상한/예산 도달은 원인과 입력을 보존한 BLOCKED, capacity 부족은 RESOURCE_WAIT로 남긴다.

## 완료·검증 기준

- V1-11/12: 실제 isolated OOM/memory eviction→증설→cold resume의 profile·fence·binding 증거가 연결된다.
- 동시 incident/watch 중복·각 단계 crash/Active 교체에서 operation/예약/새 writer가 중복되지 않는다.
- quota/Spot/disk/exit137 단독을 잘못 RAM 증설로 처리하지 않는다.
- cancel/close·새 입력 경합과 상한 도달에서도 원 입력·receipt가 유지되고 과거 UNKNOWN을 임의 재실행하지 않는다.

## 산출물·연계

recovery operation 단계·원격 장애 결과·실제 admitted 자원·native resume 증거를 제출한다. 사용자 화면에는 기존 지원 상태로 진행/대기/실패를 투영하고 별도 새 앱 RPC를 만들지 않는다.
