# P1-04 — 영속 첨부·upload/chunk/commit/abort

상태: 구현 미착수 · 단계: Phase 1 / 착수 묶음 2.
선행: [P1-02](P1-02.md), [P1-03](P1-03.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §7·§8.4. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

기존 clipboard/첨부 RPC를 Pod 수명과 분리한 durable blob에 연결한다. 공개 wire와 작은 이미지 fallback은 기존 계약을 유지한다. 수정 경계는 upload 상태/DB 참조, blob 저장·alias, 기존 첨부 handler와 provider 전달 adapter다.

## 구현 계약

1. upload/chunk/commit/abort의 기존 request/response와 payload 의미를 보존한다. chunk 순서·원 내용·완성 상태를 영속적으로 추적한다.
2. 첨부의 내구성과 참조를 확인하기 전에는 이를 포함한 Message를 accepted로 처리하지 않는다. 미완성·저장소 불가·기존 기술 제약 오류를 성공으로 반환하지 않는다.
3. 영속 blob의 안정적 alias를 통해 새 attempt에서도 같은 첨부를 전달한다. 이전 Pod의 `/tmp` 절대경로를 유일 식별자로 사용하지 않는다.
4. 접수된 Message가 참조하는 blob은 abort/정리/Pod 삭제로 제거하지 않는다. 업로드 중 자원과 접수된 참조의 수명을 구분한다.
5. 원 본문·첨부를 임의 축소·자동 분할·삭제하지 않고 새 합산 quota를 추가하지 않는다. provider의 실제 한도 초과는 입력을 보존한 전달 실패로 남긴다.

## 완료·검증 기준

- V1-02/04: chunk 중간·commit 경계·Message 접수 경계 crash와 retry에서 원 데이터/참조가 보존된다.
- 저장 실패·미완성 업로드는 accepted-without-durable-blob 상태를 만들지 않는다.
- 접수 뒤 Pod를 교체해도 동일 첨부를 실제 provider가 사용할 수 있다.
- abort/정리와 접수의 경합에서도 이미 접수된 참조가 끊기지 않는다.
- 기기별 기존 작은 이미지 fallback과 일반 upload 경로를 실제 지원 범위에 맞게 구분해 검증한다.

## 산출물·연계

upload/blob 상태 계약·기존 RPC adapter 변경·원격 장애/복구 증거를 제출한다. 공통 intake P1-05와 structured/legacy P1-17/18이 이 내구성 판정을 사용한다.
