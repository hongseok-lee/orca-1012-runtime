# P1-02 — PostgreSQL schema·객체 ID·revision·잠금 규칙

상태: 구현 미착수 · 단계: Phase 1 / 착수 묶음 1.
선행: [G-01](G-01.md). 원격 적용 환경은 [P1-01](P1-01.md)과 합류한다.
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §3·§5. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

후속 core가 함께 사용할 영속 모델·제약·transaction 경계를 구현한다. migration/schema/공용 ID·타입의 변경 소유자는 root가 하나로 지정한다. 정본의 설계용 필드 목록을 실제 DB 형태로 옮기되 계약을 임의 삭제하거나 새 lifecycle 정책을 만들지 않는다.

## 구현 계약

- Catalog: Worktree/workspace의 최종 public ID·별명·alias·provisioning·revision·tombstone, Tab과 stable terminal handle, Session의 순번/journal/context/provider binding을 보존한다.
- 실행: Runtime Unit/member/attempt, desired state, deadline, operation/step, leader lease와 실제 자원 profile·incident·recovery episode·reservation을 저장한다.
- 입력: Message와 원 Input Component, sealed revision/hash, delivery attempt, RPC receipt, legacy draft, cancel intent, session context를 분리한다. 재시도를 위해 원 Message를 복제하지 않는다.
- 기록: session event/outbox, producer 사건 큐와 append-only 시도 이력, audit, notification, replay head/event를 저장한다. Snapshot/storage 모델은 Phase 2 계약을 표현하되 기능을 활성화하지 않는다.
- `UNIQUE(session_id, seq)`, 인증 principal/scope/method/operation key의 receipt UNIQUE, producer/incarnation/seq와 canonical event identity를 보호한다.
- Runtime Unit의 active execution grant 최대 1개, 동일 실제 storage domain의 RW grant 최대 1개를 보장한다. 클라이언트 접속 수 제한으로 해석하지 않는다.
- `session_fence`, `execution_epoch`, `controller_term`, `storage_epoch`는 독립된 의미와 갱신 조건을 갖는다. 고정된 lock 순서·row revision/CAS를 사용하며 외부 K8s 응답을 기다리는 동안 DB lock을 유지하지 않는다.

## 완료·검증 기준

1. 새 dataset에 migration을 적용하고 모든 §5 테이블군/필수 제약과 실제 객체의 대응을 제출한다.
2. 동일 receipt·순번·event·grant의 동시 쓰기에서 중복이 차단되고 전체 transaction의 원자성이 유지된다.
3. serialization/UNIQUE 충돌 후 부분 입력·중복 Message·잘못된 grant가 남지 않는다.
4. 서로 다른 세대/term의 CAS를 혼용한 요청이 거절되며 원래 영속 identity는 Pod 교체로 바뀌지 않는다.
5. 사건 FAILED는 성공 `processed_at`으로 기록되지 않고 실패 이력·context 연결을 보존할 수 있다.

## 산출물·연계

migration·영속 모델·공용 계약과 DB 경합 증거를 제출한다. 개별 intake, controller, resource, replay 알고리즘은 각 작업의 소유이며 P1-02 완료만으로 해당 기능 완료를 선언하지 않는다. G-01 뒤 root가 실제 파일 분해를 확정해야 위임 준비가 끝난다.
