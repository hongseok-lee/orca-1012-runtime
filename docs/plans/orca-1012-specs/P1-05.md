# P1-05 — 공통 입력 수신함·receipt 재생·중복 경합

상태: 구현 미착수 · 단계: Phase 1 / 착수 묶음 2.
선행: [P1-02](P1-02.md)·[P1-03](P1-03.md)·[P1-04](P1-04.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §5·§8.2·§15.1. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

hot/cold·structured/legacy가 동일한 durable intake와 receipt를 사용하게 한다. 수정 경계는 입력 repository/service와 adapter가 호출하는 내부 접수 계약이다. 개별 wire 해석은 P1-17/18에서 맡는다.

## 구현 계약

1. 인증된 principal·session scope·method·operation key와 원 payload hash로 요청을 식별한다. 클라이언트가 주장하는 sender를 인증 identity 대신 사용하지 않는다.
2. 인증/대상 귀속 확인 뒤 기존 receipt를 우선 조회한다. Session/관련 Runtime Unit을 고정 순서로 잠근 뒤 receipt를 다시 조회해 동시 재접수를 차단한다.
3. 신규 요청에만 lifecycle·fence·실제 capacity·첨부 완성을 확인한다. 이미 접수된 동일 요청은 Pod 교체나 현재 용량/상태 변화로 새 요청처럼 거절하지 않는다.
4. 원 Input Component·Message 연결·submission journal·필요한 wake/reconcile 의도·outbox·receipt를 같은 transaction에 저장한다. compatible RUNNING/wake는 공유하고 실제 의도 전환에만 intent revision을 변경한다.
5. UNIQUE/serialization 충돌은 전체 rollback 뒤 같은 key/payload receipt를 재생한다. COMMIT 결과 불명은 같은 key로 조회하며 새 key를 만들어 재접수하지 않는다.
6. 같은 key의 다른 payload는 효과 없는 conflict다. 다른 key의 같은 본문은 별개 원 입력/receipt로 보존한다. raw/legacy의 실제 request ID 한계보다 강한 보장을 광고하지 않는다.

## 완료·검증 기준

- V1-02: 같은 key 동시 요청, ACK 유실, 불확정 COMMIT, 현재 fence/lifecycle/용량 변경 뒤 retry에서 최초 receipt를 재생한다.
- conflict와 transaction crash에서 중복 Component·append·wake operation이 생기지 않는다.
- V1-03: 다른 ID의 같은 본문은 Component 2개·receipt 2개, 같은 ID retry의 추가 Component는 0개다.
- DB/첨부 저장소 불가나 실제 wire 오류에서 성공 ACK를 보내지 않는다. `accepted-without-row=0`이다.

## 산출물·연계

공통 intake 계약, transaction/receipt 구현, 동시성·장애 증거를 제출한다. P1-06은 접수된 Component를 병합하고 P1-07은 취소와 실행의 승자를 결정한다. 이 작업은 외부 효과 exactly-once를 보장하지 않는다.
