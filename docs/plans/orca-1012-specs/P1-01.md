# P1-01 — 새 개발 실행 환경·영속 저장소·원격 검증 환경

상태: 구현 미착수 · 단계: Phase 1 / 착수 묶음 1.
선행: [O-01](O-01.md), [G-01](G-01.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §4.1·§14–15. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

새 dataset epoch에서 Agent/Orca/PostgreSQL 실행 환경과 원격 build/test 기반을 마련한다. 수정 경계는 인프라 선언·스토리지 배치·실행 이미지/설정·복구 절차다. 실제 파일과 적용 대상은 G-01 뒤 root가 지정한다.

현재 기존 클러스터/NFS 공유 mount와 그 테스트 Pod는 없다. 이 작업에서 새 환경과 Agent 영속 공유 저장소를 마련하고 실제 endpoint/export/mount·원격 실행 경로를 확인해 기록한다. 옛 NFS 주소를 현재 문서 읽기나 실행 경로로 재사용하지 않는다.

사용자 후속 지시에 따른 배치는 클러스터 내부 PostgreSQL Pod + 전용 block PV, 클러스터 내부 NFS 서버 Pod + SSD PV, NFS에 홈 디렉터리를 두는 Agent Pod다. Cloud SQL/Filestore 도입을 전제로 하지 않는다. 개발 기반 준비에서 구성한 부분과 이 ID의 WAL 복구·실제 영속성 전체 합격을 구분한다.

## 구현 계약

1. Agent 홈/checkout과 공용 자료를 구분한다. 기본 배치를 전역적인 Agent·Session·디렉터리 1:1 불변식으로 확대하지 않는다. 공유 디렉터리 접근은 P1-10의 RO/RW 계약을 따른다.
2. 새 dataset epoch와 작업 디렉터리를 사용해 새 별명/ID가 과거 provider 이력을 우연히 재사용하지 않게 한다. 과거 데이터 이관기는 만들지 않는다.
3. PGDATA/WAL은 Agent의 일반 NFS 홈과 분리한 영속 block volume에 둔다. `fsync`·`synchronous_commit`을 유지하며 영속 commit 후에만 접수 성공이 가능해야 한다.
4. Agent·Orca Serve·PG Compute의 Spot 조건과 디스크 보존 정책을 기록한다. 동일 PG 디스크/WAL 재기동 시에도 동시 DB writer가 없도록 차단을 확인한다.
5. 원격 테스트/빌드 실행 경로, 이미지 식별자, 지속할 빌드 캐시와 접근 조건을 마련한다. 오케스트레이션 호스트를 제품 빌드/런타임 시험기로 사용하지 않는다.
6. 관리 VM `<protected-admin-vm>`, `<protected-admin-disk>`, 기존 백업 전체·계정 자격·공유 인프라·동결 템플릿을 보존한다. 남은 옛 클러스터 디스크를 이 작업으로 자동 삭제하지 않는다.

## 완료·검증 기준

- 실제 구성/이미지/스토리지 revision과 새 dataset epoch를 확인한다.
- PG Compute Spot 회수 후 같은 WAL로 복구되며 이전 commit이 유지된다. DB 불가 중 성공 ACK를 보내지 않는다.
- DB 저장소와 Agent NFS가 실제로 분리되고 동시에 두 DB writer가 생기지 않는다.
- 백업·복원 절차와 검증 범위를 기록한다. 단일 PG를 HA라고 표시하지 않고 과거 시점 PITR 자동화는 C-01로 구분한다.
- 원격 build/test 접근과 캐시 보존 경로를 확인한다. 실제 Agent 최소 자원·배치 합격은 G-03 증거로 별도 판정한다.

## 산출물·연계

인프라 변경, 실제 자원/저장소 inventory, 원격 실행 경로, WAL 복구·백업/복원 증거를 제출한다. P1-02 및 공통 Port 작업과 계약 확정 후 병렬 진행할 수 있다. 실제 기능 합격은 후속 작업에서 판정한다.
