# P1-03 — 공통 transaction·journal·outbox·감사 기록

상태: 구현 미착수 · 단계: Phase 1 / 착수 묶음 2.
선행: [P1-02](P1-02.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §5·§10.8.10·§13. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

접수·상태 변경·출력·사건 처리가 동일한 영속 기록 원칙을 사용하도록 transaction과 publish 기반을 만든다. 수정 경계는 DB transaction helper/repository, canonical event identity, journal/outbox publisher, audit 기록이다.

## 구현 계약

1. 업무 상태 변경과 그 receipt/journal/outbox를 같은 transaction에 넣는다. commit되지 않은 결과를 성공 ACK나 영속 출력으로 발행하지 않는다.
2. publish는 commit 후 수행한다. 발행 전 crash나 응답 유실 이후 미발행 outbox를 재조회해 이어간다. 알림은 힌트이며 DB가 정본이다.
3. provider-native identity/lineage, producer incarnation/sequence를 canonical event와 연결해 재전송을 dedup한다. Snapshot 메모리의 옛 sequence만을 새 이벤트 유일 키로 사용하지 않는다.
4. actor·Session·Runtime Unit·operation·attempt·Pod/Node UID·profile revision과 원인/상태 전이·발생/수신/commit 시각을 연결한다.
5. DB 불가·불확정 COMMIT을 실패/불명으로 정확히 다룬다. 원 입력/credential을 일반 인프라 로그에 넣지 않고 보호된 evidence 참조를 사용한다.
6. 전역 replay의 commit 순서 offset은 P1-25가 담당한다. 단순 event 번호나 발생 시각을 그 순서라고 가정하지 않는다.

## 완료·검증 기준

- V1-02: transaction 전/중/직후 crash에서 부분 상태와 accepted-without-row가 0이다.
- commit 후 publish 전 crash·중복 publish에서 동일 canonical event로 수렴하며 기록이 누락되지 않는다.
- 불확정 commit은 원 key/identity로 조회할 수 있다. 성공 여부를 추측해 새 업무 효과를 만들지 않는다.
- DB 장애 구간의 producer spool과 gap 여부를 정직하게 기록하며 미저장 출력을 영속 결과처럼 내보내지 않는다.
- audit로 한 operation의 상태 전이와 원인을 추적할 수 있고 장기 키/본문이 불필요하게 복사되지 않는다.

## 산출물·연계

공통 저장/발행 계약, 실패 경계 시험, 실제 기록·publish 대응 증거를 제출한다. 입력 접수 P1-05, 사건 큐 P1-12, 출력 P1-20, 알림/replay P1-25가 이를 사용한다.
