# P1-28 — 입력부터 출력까지 단계별 지연 계측

상태: 구현 미착수 · 단계: Phase 1 / 착수 묶음 4.
선행: [P1-03](P1-03.md)·[P1-11](P1-11.md)·[P1-14](P1-14.md), [P1-17](P1-17.md)~[P1-20](P1-20.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §15.2. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

수신부터 provider 처리·파일 감지·journal·구독 전달까지 어디서 지연이 생기는지 구분한다. 수정 경계는 기존 ID와 연계한 timestamp/trace·원격 probe·측정 보고다. 계측 ID와 기록 설계는 앞선 core 작성 때부터 포함한다.

## 계측 계약

1. intake 수신/commit, queue/dispatch/provider admission, wake·scheduling·이미지 시작, provider generation/최초 출력·완료를 분리한다.
2. provider 출력 파일의 생성/감지, adapter 수신, journal commit, publish, 구독 probe 수신을 분리한다. commit 이전 파일 감지 지연을 누락하지 않는다.
3. Session/Message/operation/attempt/epoch/provider/path별로 상관관계를 남긴다. 본문·credential을 trace에 자동 복사하지 않는다.
4. hot, cold, reconnect, 의도적 file-detection 지연 주입의 네 경로를 측정한다. first와 completed, generation과 전달/복구를 따로 보고한다.
5. sample 수·분포·clock 오차·미측정 구간·환경/image/config revision을 기록한다. 다른 시계 timestamp를 검증 없이 빼거나 단일 표본을 p95라고 부르지 않는다.

## 완료·검증 기준

- V1-15에서 각 경로의 pre-journal 병목과 post-commit 전달을 구분할 수 있다. 파일 감지 지연 주입이 해당 구간에 나타난다.
- 초기 목표인 intake commit p95<300ms, 기존 기록 첫 응답 p95<500ms, provider event commit→구독 전달 p95<1초를 해당 경계/표본과 함께 보고한다.
- 목표 미달과 원인을 숨기지 않고 root가 완료 여부를 판정한다. scheduling/generation/복원 시간을 위 목표와 혼합하지 않는다.
- 실제 앱 rendering은 별도 실기기 증거가 없으면 미측정이다. 과거 단일 표본 344ms/2776ms·NFS 9843ms를 현재 p95로 재사용하지 않는다.

## 산출물

계측 변경·원격 raw 측정 참조·경로별 지연 보고와 제한을 제출한다. commit→subscribe만 빠르다는 결과로 전체 E2E 통과를 선언하지 않는다.

## 병렬 납품 경계

P1-03부터 공통 trace 계약·probe를 준비한다. 제품 파일의 계측 hook은 각 기능 변경 소유자가 반영하고 계측 worker가 같은 파일을 동시에 수정하지 않는다. 개발 서버로 구간별 측정을 진행하되 최종 분포는 P1-14 공개 HA 통합과 나머지 선행 경로 준비 뒤 고정된 revision/환경에서 수집한다.
