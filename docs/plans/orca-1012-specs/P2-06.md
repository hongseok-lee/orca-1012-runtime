# P2-06 — 실행 중 150% 초과 live in-place 증량

상태: 구현 미착수 · 단계: Phase 2 / 착수 묶음 6.
선행: [P1-21](P1-21.md)~[P1-23](P1-23.md), [P1-30](P1-30.md). Snapshot/P2-07은 선행이 아니다.
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §10.8.9·§18.1–2. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

살아 있는 실행의 request 대비 사용량이 임계를 넘으면 같은 Pod에서 증량한다. 수정 경계는 신뢰 표본 trigger, growth operation/reservation, runtime resize·실제 상태 조회와 실패 복구다.

## trigger·성공 계약

1. 대상 container의 `usage > 1.5×admitted_request` 첫 신뢰 표본을 CAS해 하나의 growth operation을 만든다. working-set/RSS·계측 대상을 명시하고 Pod 총량을 단일 container request와 비교하지 않는다.
2. 기본 target은 2배이며 더 큰 실제 수요가 있으면 기존 상한/예산 안에서 반영한다. OOM 복구와 episode·growth 예산을 공유해 동시에 이중 증설하지 않는다.
3. 같은 Pod에 in-place 요청하고 actual applied resources와 동일 프로세스/메모리 연속성을 확인한다. API ACK만으로 성공 처리하지 않는다.
4. live resize만으로 execution epoch를 바꾸지 않는다. admission 비율 등 필요가 없으면 CPU request를 유지하고 memory limit을 추가하지 않는다.
5. 별도 node-headroom gate·노드 선택 제어를 만들지 않는다. request 증량을 물리 RAM 추가나 OOM 방지 보장으로 표현하지 않는다.

## 이 작업 자체의 실패 계약

- Deferred/Infeasible/timeout은 실제 적용·진행 상태를 재조회하고 영속된 유한 기한으로 처리한다.
- 단순 응답/관측 timeout 하나로 살아 있는 작업을 즉시 죽이거나 같은 증량을 두 번 요청하지 않는다. 이미 적용됐으면 기존 operation 결과를 인수한다.
- 적용 불가/실패가 확정되면 현재 실행 상태를 먼저 확인하고 기존 writer를 안전하게 회수한 뒤 목표 profile의 cold 경로로 복구한다.
- 입력·receipt·UNKNOWN·취소 이력과 provider readiness 계약을 유지한다. 실제 OOM이 먼저 발생하면 같은 incident/episode로 reactive 복구와 합류한다.
- 이 실패 경로는 Snapshot/복원 후 증량 구현 없이도 자체 구현·검증한다. RV-02 보완에 따라 P2-07의 시험으로 대신하지 않는다.

## 완료·검증 기준

실제 Agent에서 임계 최초 표본/중복 표본/동시 OOM, live 성공, 적용 후 ACK 유실, Deferred/Infeasible·기한 초과, 안전 cold fallback을 각각 검증한다. Pod/process/memory 연속성, 실제 applied profile, 단일 operation/예산, 입력 보존 증거가 필요하다. 과거 합성 same-node 성공만으로 활성화하지 않는다.

## 산출물

trigger/resize/fallback 구현과 성공·실패별 원격 증거를 제출한다. 1초 관측은 초기 목표이며 임계 관측 전에 eviction이 일어날 가능성을 숨기지 않는다.
