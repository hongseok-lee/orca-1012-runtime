# P1-06 — Input Component 병합·Message dispatch 봉인

상태: 구현 미착수 · 단계: Phase 1 / 착수 묶음 2.
선행: [P1-05](P1-05.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §8.3·§9.2.1·§15.1. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

dispatch 전에 같은 Session의 일반 입력을 하나의 pending Message로 병합하되 원 입력과 receipt를 잃지 않게 한다. 수정 경계는 pending Message 선택/append, input 순번, dispatch claim과 sealed payload 구성이다.

## 구현 계약

1. 같은 Session의 아직 봉인되지 않은 일반 입력 묶음만 병합한다. 원 Input Component의 순서·발신자·본문·첨부·operation ID·receipt 연결을 개별 보존한다.
2. 새로운 입력을 append할 때 Message revision을 갱신한다. 다른 operation ID의 동일 본문도 추가 Component로 남긴다.
3. dispatch claim은 정확한 Message revision과 payload hash를 원자적으로 봉인한다. 봉인 이후 도착한 일반 입력은 다음 Message에 배치한다.
4. slash/command, 질문·승인 응답, raw 입력 등 의미가 다른 입력을 일반 본문으로 합치지 않는다. 해당 입력의 순서 경계를 유지한다.
5. 같은 요청 retry는 P1-05 receipt로 처리하고 병합 본문에 다시 append하지 않는다. Session lock/claim과 append의 승자를 일관되게 결정한다.
6. 합산 크기·개수 상한으로 임의 분할·요약·삭제하지 않는다. 실제 provider 제약으로 전달할 수 없으면 원 입력과 실패를 보존한다.

## 완료·검증 기준

- V1-03: dispatch 전 일반 입력 100개가 원 Component 100개와 개별 receipt를 보존한 Message 1개가 된다.
- claim 직전/직후 동시 입력에서 봉인 revision/hash가 바뀌지 않으며 이후 입력은 다음 묶음으로 간다.
- 다른 ID의 같은 본문 두 건은 Component/receipt 각각 2개다. 봉인 전이면 Message 1개, 봉인 경계를 사이에 두면 2개다.
- slash/질문/raw 경계와 다중 클라이언트의 순서를 유지한다. crash/retry 후 원문이나 첨부가 빠지지 않는다.

## 산출물·연계

병합/봉인 계약·원문 매핑·경합 시험 증거를 제출한다. P1-07의 pending 취소는 봉인 대상 묶음과 연결하고, P1-09/11의 dispatch에는 봉인된 identity와 hash를 전달한다.
