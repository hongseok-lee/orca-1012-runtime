# P1-22 — 자원 profile·동시 reservation·유한 복구 예산

상태: 구현 미착수 · 단계: Phase 1 / 착수 묶음 3.
선행: [P1-02](P1-02.md)·[P1-03](P1-03.md)·[P1-21](P1-21.md). 완료 gate: [G-03](G-03.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §10.8.3–6. [공통 계약](COMMON.md)의 정확한 초기 정책값을 적용한다.

## 목적과 수정 경계

증설·축소·교체가 하나의 영속 profile/예산을 공유하도록 만든다. 수정 경계는 versioned resource policy/profile, reservation, episode/rolling counter와 admission 비교다.

## 구현 계약

1. 신규 Agent만 실제 검증된 최소 profile로 시작한다. 기존 Agent는 sleep/wake/Spot 후에도 마지막 승인 크기를 유지한다.
2. 대상 container의 실제 admitted request R과 귀속된 신뢰 peak P로 `round_up_profile_step(max(2×R, 1.25×P))`를 계산하고 effective cap으로 제한한다. P가 없으면 2×R, target>R일 때만 증설한다.
3. 기본 cap 16Gi, growth budget `ceil(log2(effective_cap/minimum_request))`, Runtime Unit 기준 rolling 24h 예산, replacement=growth budget+3을 versioned policy로 저장한다. 초기 제안값을 불변·실측 적정값으로 표시하지 않는다.
4. CPU:RAM·sidecar/initContainer·quota·총예산·동시 예약을 포함한다. 실제 memory limit 생략·CPU limit 미설정·Spot·1 Runtime Unit/Node를 확인하고 다른 Agent 삭제로 capacity를 확보하지 않는다.
5. 같은 operation의 reservation을 재사용하고 만료 시 실제 Pod 생성 여부를 먼저 조회한다. steady-state와 old/new 중첩 비용을 구분하며 외부 controller의 소비까지 자체 예약이 막는다고 가정하지 않는다.
6. scheduling/quota 부족은 RESOURCE_WAIT이며 새 메모리 부족 증거 없이 다시 2배로 키우지 않는다. 실제 생성 후 admitted/applied 값이 승인 범위를 벗어나면 실행을 열지 않는다.
7. 영향 작업 완료/명시 해결과 실제 활동 30분 OOM 없음으로 episode를 안정화한다. Ready·Pod 이름 교체·idle만으로 예산을 초기화하지 않고 learned floor를 24h 보호한다.

## 완료·검증 기준

V1-11/12에서 최소→상한, peak 반영 단계 건너뛰기, cap 도달, 동시 OOM reservation, 만료/응답 유실, quota/CPU:RAM 조정, sleep/wake·Active 교체를 검증한다. 실제 policy revision과 승인/적용 자원·counter가 일치하며 예산 소진은 입력을 보존한 BLOCKED다.

## 산출물·연계

정책/profile·예약·예산 구현과 실제 admission/경합 증거를 제출한다. P1-23/24와 P2-06/07은 이 정책을 사용한다. 과거 burst 여유·최소 admission만으로 현재 실행 능력을 과장하지 않는다.
