# P1-25 — PG 알림 센터·commit 순서 replay stream

상태: 구현 미착수 · 단계: Phase 1 / 착수 묶음 3.
선행: [P1-03](P1-03.md)·[P1-12](P1-12.md).
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §10.8.10·§13.1. [공통 계약](COMMON.md)을 적용한다.

## 목적과 수정 경계

사건·복구 실패·알림을 재연결과 Active 교체에도 빠짐없이 조회한다. 수정 경계는 notification 상태/dedup, PG replay stream-head/event와 outbox 발행 transaction이다.

## 구현 계약

1. incident/operation 기준으로 알림을 dedup하고 대상·원인·최초/최근 시각·재시도·가능한 조치를 기록한다. 읽음과 실제 해결을 분리하며 조건 회복 시 해결 상태를 갱신하고 이력을 남긴다.
2. commit된 원본 사건을 발행할 때 PG stream-head를 잠그고 다음 offset 할당·replay row 삽입·outbox 완료를 같은 transaction으로 수행한다.
3. 전역 `(stream_epoch, offset)`을 HTTP 페이지와 SSE, Agent 필터에 공통 사용한다. bare BIGSERIAL 할당 순서나 occurred_at을 commit 순서 cursor로 사용하지 않는다.
4. source event ID UNIQUE로 재발행을 dedup한다. 늦게 들어온 과거 사건도 새 publish offset을 받아 이미 본 cursor 이후 조회에 나타나야 한다.
5. 보존 범위 밖 cursor는 reset/resync를 명시한다. 전역 발행 순서를 모든 Agent 업무의 전역 직렬화로 확대하지 않는다.
6. DB 장애 중 가능한 producer spool로 보존하고 유실 관측은 gap으로 기록한다. 미저장 연결 오류 표시를 영속 알림 저장 성공으로 위장하지 않는다.

## 완료·검증 기준

- V1-13/14: 앞서 번호를 얻은 transaction의 늦은 commit, 동시 publisher, publish ACK 유실에서도 cursor로 영구 누락되는 사건이 없다.
- 100까지 읽은 뒤 늦은 과거 사건이 101 이후 새 offset으로 보인다. 페이지→SSE·Active 인수·필터 변경에서 같은 계약을 유지한다.
- 중복 사건의 알림 폭증이 없고 읽음만으로 해결되지 않는다. 실제 조건 회복은 해결 상태와 이력에 반영된다.
- reset과 DB 장애/gap이 정직하게 표현된다.

## 산출물·연계

notification/replay 구현, commit 순서·재연결 증거를 제출한다. P1-26/27이 이를 사용하며 UNKNOWN 전용 강제 해결/재실행 기능은 만들지 않는다.
