# G-01 — 현재 소스·배포 revision·원격 빌드 경로 확인

상태: 증거 미확보 · 구분: 구현 착수 경계 확인.
선행: 보존된 정본과 저장소 읽기. 연계: P1-01/02 및 모든 후속 위임.
근거: [1012 정본](../../reference/haagent-20261012/plans/orca-durable-session-snapshot-rpc-spec-20261010.md) §2·§15·§17. [공통 계약](COMMON.md)을 적용한다.

## 목적과 범위

현재 제품/플랫폼 소스와 실제 실행물의 관계를 확인해 root가 수정 파일과 단일 소유자를 정할 수 있는 사실 자료를 만든다. 역사적 `<historical-source-worktree>`나 과거 HEAD를 현 배포본으로 가정하지 않는다. 이 작업은 구현 설계나 새 작업목록을 worker에게 맡기는 작업이 아니다.

## 확보할 계약·자료

1. 실제 repository root, branch/HEAD, dirty/untracked patch의 위치·보존 상태, build 입력과 image digest의 대응을 기록한다. 확인할 수 없는 대응은 불명으로 표시한다.
2. §17의 공개 schema, Session/Tab/Catalog, structured/legacy adapter, Stop 대상 매핑, runtime gateway, lifecycle 및 상태 projection이 현재 어느 파일에 있는지 연결한다.
3. root가 변경 충돌을 판정할 수 있도록 공용 migration/schema/Port/type의 참조 관계와 기존 수정 사항을 보고한다. worker가 작업 경계·우선순위를 독자 확정하지 않는다.
4. 원격 build/test 실행 위치, 이미지 publish/pull 경로, 지속할 빌드 캐시와 접근 조건을 확인한다. 사라진 옛 클러스터의 테스트 Pod를 사용 가능하다고 표시하지 않는다.
5. 임시 경로에만 남은 필요한 소스가 있으면 출처·revision을 유지해 정식 관리 경로로 보존할 구체 대상을 보고한다. 기존 미커밋 변경을 덮어쓰지 않는다.

## 완료·검증 기준

- source→patch→build→image의 확인된 관계와 빈 구간이 목록으로 남는다.
- §17 경계마다 실제 파일 경로와 확인 revision이 있다. 존재하지 않는 과거 파일을 새 구현의 수정 대상으로 쓰지 않는다.
- 원격 실행 환경이 없으면 P1-01의 구축 산출물과 연결하며 준비 완료로 표시하지 않는다.
- root가 위임 전 각 작업의 수정 파일, 공통 파일 소유자, 선행 계약과 원격 증거 위치를 확정할 수 있다. 실제 파일 분해를 하지 못한 작업은 위임 준비 미완료다.

## 산출물과 범위 밖

소스/실행물 대응표, 공용 파일 경계 자료, 원격 build/test·cache 경로와 미확인 사항을 제출한다. 이 gate 자체가 제품 기능 구현·전체 코드 감사·배포를 완료했다는 뜻은 아니다. RV-07의 파일 범위 우려는 이 증거와 root의 구체 위임으로 닫는다.
