# P126 / P127 HTTP API source 납품

Root가 지정한 HTTP / UI 첫 연결 계약의 API 소유 source입니다. PR43 원 `dae68ae347442d9d0300a645874bc4619120c5d3`에서 시작했으며, source 교정 `e1822db1dd8d3716189f93725fcec13956d4c4f8`과 최신 자산 pin `e1d747b54433533062d28b76a8687c3fcaf3f249`를 소비했습니다. 중단된 12개 파일은 수정 없이 `7c2ce019332770205b0b4ed9b23a89be3b2b5dc0`에 보존했습니다. PR22 / PR35 / PR40의 원 source, 시험과 PNG를 재실행하거나 변경하지 않았습니다.

`ops/contract.ts`는 UI가 읽는 Unit / 상세 / operation / event cursor / notification / command DTO를 제공합니다. `createOpsHttpHandler(config: OpsHttpConfig): OpsHttpHandler`는 요청을 소유하면 true, 아니면 false를 반환합니다. UI 접점 `OpsUiProvider`는 `(pathname: string) => OpsUiAsset | null | Promise<OpsUiAsset | null>`이고 `OpsUiAsset`은 `{contentType,body}`입니다. UI provider에 actor나 key를 전달하지 않습니다. 첫 DTO 이후 `attempt.podUid`는 저장 column의 nullable 사실에 따라 null을 허용하며, 기본 003에 없는 incident state / revision도 null로 표시합니다.

`createPgOpsServices(config: OpsPgConfig)`는 실제 P113 `readUnitProjectionInTransaction` / `requestUnitIntent`와 P125 `readReplayPage` / `listNotifications` / `markNotificationRead`를 직접 소비합니다. 8개 route와 기존 receipt의 COMMITTED / REPLAYED / UNCERTAIN 구분을 연결했습니다. 서버 dataset / namespace / 허용 workspace 집합과 불변 014 workspace → Unit 관계로 귀속을 확인합니다. 현재 OPEN member만으로 원 receipt 접근을 제한하지 않습니다. 전역 replay scan cursor와 notification nextAfterId는 숨겨진 row가 있어도 진행합니다.

Config의 primitive 값과 callback / 원 receiver는 handler 생성 시점에 고정합니다. 인증 완료 직후 actor scope를 소유한 배열로 복사하고 다음 await 전에 고정합니다. PG services의 namespace / workspace 집합과 lifecycle policy도 생성 시 고정합니다. SQL callback의 권한 / 존재 오류는 `DurableDatabaseError`의 좁은 `OPS_TARGET_FORBIDDEN` / `OPS_UNIT_MISSING` / `OPS_OPERATION_MISSING` / `OPS_NOTIFICATION_MISSING` code를 사용하고 HTTP 경계에서 403 / 404로 매핑합니다. 공통 transaction wrapper와 `safeDatabaseError`는 변경하지 않았습니다.

Optional server 구성은 `opsHttp?: RuntimeOpsHttpConfig`입니다. Runtime은 실제 `DeviceRegistry.validateToken`을 호출하는 `createDeviceRegistryOpsVerifier`를 제공합니다. Fingerprint는 실제 인증 후 principal 식별에만 사용합니다. Cookie-only 요청은 인증되지 않으며 cookie/session을 발급하지 않습니다. 인증과 Origin을 대조하고 no-store / sanitized 오류를 반환합니다. 키를 query / HTML / 로그에 전달하지 않습니다.

`runtime-rpc-pairing-types.ts` / `runtime-rpc-state.ts`에는 Root가 허가한 optional ops 필드만 연결했으며 기존 `durableCatalogRead` 정의와 구성은 보존했습니다. `runtime-rpc-lifecycle.ts`와 `ws-transport.ts`는 같은 listener에서 ops / 기존 static handler를 합성합니다. WS upgrade는 원 경로를 사용합니다. `stop()`은 소유 unary / SSE 응답을 실제 종료하고 timer / drain / disconnect listener를 정리하며, 완료가 늦은 callback 결과는 쓰지 않습니다. 실행 중인 PG query 자체를 취소하거나 공용 pool을 종료하지 않습니다. `orcad-entry.ts`와 UI 소유 source는 변경하지 않았으며 startup 활성화는 아직 아닙니다.

`first-handler.pg.test.mts`에 신규 최초 callback 9개를 준비했습니다. 실제 기존 키 verifier와 실제 PG services를 원 HTTP handler에 연결하며, 지정 auth / origin / namespace / empty와 failure / receipt replay·conflict·uncertain / page→SSE / reset / stop·disconnect / 읽음과 해결 구분 / 조회의 wake 0 경계를 확인하도록 작성했습니다. 공통 기존 fixture helper를 재사용하고 DDL은 작성하거나 복제하지 않습니다. DB owner가 지정 migration을 적용한 별도 `orca_p126_*` DB만 받습니다. Commit 응답 손실은 실제 COMMIT 뒤 driver 응답을 버리는 fixture이며 실제 네트워크 장애 합격이 아닙니다. 최초 준비 source의 미실행 상태는 아래 실제 검증 결과로 갱신했습니다. Runtime/startup 활성화와 실제 API를 사용하는 UI 캡처는 아직 아닙니다.

Root의 2026-10-14 한정 위임으로 `lifecycle/projection.ts` 한 파일에서 `readUnitProjectionInTransaction(tx, id)`를 추출했습니다. 원 SQL literal, `LIFECYCLE_UNIT_MISSING` 오류와 정형값을 그대로 유지하며 기존 pool wrapper는 이 entry를 호출합니다. Ops 목록은 namespace / Unit 기본 projection / counts / mounts / DB 조회 clock를, 상세는 같은 Unit projection과 상세 행을 각각 응답 단위의 하나의 `REPEATABLE READ READ ONLY` transaction에서 읽도록 작성했습니다. 다른 P113 파일과 공통 DB wrapper는 변경하지 않았습니다. 최초 PG/HTTP callback 9개는 모두 통과했습니다. Unit `observedAt`은 실제 저장 관측 시각 근거가 없어 null이며 목록의 DB 조회 시각과 구분합니다. `inputComponents`는 pending message와 실제 `(message_id, session_id)` FK로 연결한 원 component 수이고 역사적 행을 삭제하지 않습니다. 기존 callback 9개 중 namespace 사례 한 개에 목록 / 상세의 실제 SELECT await 중 다른 connection이 Unit revision / message 상태 / mount / Session을 변경하는 경계를 준비했습니다. 같은 응답의 기존 snapshot과 다음 응답의 변경된 snapshot, pending에서 제외된 component의 원 행 보존을 확인한 최초 callback 결과는 9개 PASS, fail / skip 0입니다. 합류하지 않은 자원·telemetry·node·spot·alias는 null이고, state-only operation result는 원 prompt / blob을 포함하지 않습니다. Controller 미연결 상태에서 wake는 disabled와 사유를 제공하고, SQL 접수를 실제 명령 완료로 표시하지 않습니다. 첫 납품은 전체 P126 / P127, Browser 자동 인증·screencast, native 앱 또는 HA 완료를 의미하지 않습니다.


## 실제 최초 검증과 한정 교정

고정 main `47c9a5dfa617d32dbcf43a6eda6320e853f360e1`에 소유 source를 합성했고, 원 PG 실행 pin은 `3f13bc952392302de59b13ed1add81e1408d53bd`입니다. 새 소유 DB에 원 001–018 SQL을 한 번 준비했으며 callback 9개가 9개 PASS, fail 0, skip 0, cancelled 0으로 종료했습니다. 실제 값 import 14개를 기록했습니다. 기존 cache에서 필요한 파일 4,762개를 hash 대조해 재사용했고 누락 9개 파일만 전달했습니다. 전체 checkout / node_modules 복사와 설치를 하지 않았습니다.

최초 type / lint의 원 실패를 보존했습니다. `13da77014fa533f5ce0e61505cc7a62160f0f6d5`에서 재귀 payload의 type-only 표현과 동일한 lint 표현만 교정했습니다. 소유 type root 18개 진단은 0이며 범위 밖 25개 진단은 원문과 함께 분리해 유지합니다. 전체 compiler CLI는 여전히 exit 1이므로 전체 type PASS가 아닙니다. 소유 lint 18개 파일은 exit 0, 오류 / 경고 0입니다. TS7에 없는 compiler API 경로를 참조한 별도 준비 오류도 보존하고 실제 `bin/tsc`로 확인했습니다. 성공 PG와 schema 준비를 반복하지 않았습니다.

Root가 지정한 `285b4a71e472c7be12cfdcfa98c876202ebdecf6`은 `ws-http-handler.ts`로 static listener / optional ops → static → 404 조합을 추출했습니다. `ws-transport.ts`는 import와 helper 호출로 연결하며 TLS / stop / WS 경로를 바꾸지 않았습니다. helper와 transport 2개 파일의 좁은 type / configured lint가 모두 exit 0입니다. 기존 WS suite는 반복하지 않았습니다. 원 main47과 추출 전 source의 파일·설정·actual lint exit·줄수 비교를 따로 보존했습니다. 추출 전 307 / 최대 300 진단은 현재 실제 lint에서 해소됐으며, 원인 귀속의 최종 수용은 Root 검토 사항입니다.

PR48의 이미 수락된 desktop / mobile PNG를 synthetic DTO 소비 화면으로만 재사용합니다. 원 UI source `2b7fd5a681fa592d45d2b69d30ff88d1e1566892`와 원 API contract `93c93be939cc8a68c131941c8b981494d6c6ac3f`의 캡처이며 새 촬영·이미지 편집을 하지 않았습니다.
